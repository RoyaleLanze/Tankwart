# 0016 – Mehrsprachigkeit mit i18next und expo-localization

- **Status:** Accepted
- **Datum:** 2026-11-27
- **Entscheider:** @RoyaleLanze

## Kontext

Die englische Oberfläche (#59) ist NICE-TO-HAVE und kommt nach den MUSTs. Das Fundament wird aber vorgezogen (#97, Entscheidung @SealJonny, 26.11.2026): Je später Texte über Schlüssel laufen, desto mehr Screens mit festen deutschen Texten müssten am Ende in einer sehr großen PR umgebaut werden. Vorbild ist der Dunkelmodus (ADR 0013). Gebraucht werden die Gerätesprache, eine Übersetzungsbibliothek mit Plural-Unterstützung und eine Sprache für `lib/format.ts`. Die Fehlercodes aus ADR 0014 müssen auf Texte abgebildet werden.

Prüfung auf reactnative.directory (27.11.2026): `i18next` ist für Android und die New Architecture gelistet, ohne native Abhängigkeiten, MIT, ca. 37 Mio. Downloads pro Woche, letzter Release vom selben Tag. `expo-localization` ist das offizielle Expo-Paket (Expo Go, New Architecture, Config-Plugin vorhanden).

## Optionen

1. **i18next + react-i18next:** Quasi-Standard, aktiv gepflegt, typisierte Schlüssel über `CustomTypeOptions`, Plural nach CLDR-Regeln über `Intl.PluralRules`, synchrone Initialisierung mit gebündelten Ressourcen. Dafür zwei Pakete und mehr Konfiguration.
2. **i18n-js:** Klein und einfach. Dafür keine typisierten Schlüssel, ein eigenes Pluralformat und ein kleineres Ökosystem.
3. **Lingui:** Gute Entwicklererfahrung. Dafür Compiler-Makros und eine eigene Babel-Konfiguration, die zu Expo und React Compiler zusätzliche Reibung bringt.

Die Gerätesprache kommt in allen Fällen aus `expo-localization` (`getLocales()`).

## Entscheidung

Wir nehmen Option 1, weil sie als einzige Schlüssel typisiert prüft und Plural ohne Eigenbau liefert.

- **Texte:** eine TypeScript-Datei pro Sprache in `src/locales/` (vorerst nur `de.ts`), nach Bereichen gruppiert (`common`, `auth`, `vehicles`, `refuelings`, `stations` …).
- **Typen:** Die Schlüssel werden über die i18next-Typerweiterung aus `de.ts` abgeleitet. Ein falscher Schlüssel ist ein Typfehler. Weitere Sprachen müssen dieselbe Struktur haben.
- **Setup:** `src/lib/i18n.ts` initialisiert synchron mit gebündelten Ressourcen (kein Ladeflackern) und wird einmal im Root-Layout importiert. Die Sprache wählt die reine Funktion `resolveLanguage` in `src/lib/language.ts`: die erste Gerätesprache, die die App unterstützt, sonst Deutsch.
- **Formatierung:** `lib/format.ts` nutzt die aktive i18next-Sprache (nicht direkt die Gerätesprache) und bildet sie auf eine Locale ab (`de` → `de-DE`). Zahlen, Währung und Datum bleiben beim eingebauten `Intl`.
- **Fehlertexte:** Die Logik liefert weiter Codes (ADR 0014). `messages.ts` bildet Codes auf Schlüssel ab statt auf feste Texte. ADR 0014 hat dazu einen Nachtrag.
- **Regel:** Neue UI nutzt ausschließlich Schlüssel (Eintrag in `CLAUDE.md`).

Neue Abhängigkeiten: `expo-localization`, `i18next`, `react-i18next`.

## Konsequenzen

- `expo-localization` ist ein natives Modul, deshalb ist einmal ein neuer Build nötig (`npm run android`). Das Config-Plugin ist ohne Optionen eingetragen. `supportedLocales` (Sprache pro App in den Systemeinstellungen) kommt erst mit Englisch in #59.
- Plural läuft über `Intl.PluralRules` der Hermes-Engine, ohne Zusatzpaket. Pluralformen stehen als `key_one` / `key_other` in der Textdatei.
- Die Sprache wird beim Start gelesen. Wechselt der Nutzer die Systemsprache bei laufender App, greift das erst nach dem Neustart.
- Jeder neue Text braucht einen Schlüssel statt eines Literals. Das kostet etwas Schreibaufwand und spart die große Umstellung später.
- Im Übergabegespräch erklären können: warum Schlüssel statt Texte im Code, wie die Typen aus `de.ts` entstehen und warum `format.ts` der UI-Sprache folgt statt der Gerätesprache.
